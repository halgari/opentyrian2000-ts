# Gameplay Core Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Port the in-level game so that `demo.1`–`demo.5` replay frame-identically to the C oracle and play in the browser.

**Architecture:** C globals live in one typed `ctx.game` world. Modules under `src/game/` are ported function by function from `tyrian2.c`, `mainint.c`, `varz.c`, `shots.c`, `backgrnd.c` and `config.c`. A per-frame CRC and a state trace from a patched C oracle verify the result and locate divergences.

**Tech Stack:** TypeScript, vitest, existing foundation and audio modules, C oracle patch.

**Spec:** `docs/superpowers/specs/2026-10-09-gameplay-design.md`. The **survey** is
`docs/superpowers/specs/2026-10-09-gameplay-survey.md`: every implementer reads the survey sections named in their task. It holds the C line references, the quirks and the draw order.

## Global Constraints

- **C source of truth:** `reference/opentyrian2000/src/`, pinned commit `aad5aca01af139c0b089237c38ef765f7a84355d`. Read each C function **in full** before porting it. Every ported function carries `// port of <fn> (<file>.c)`.
- **File header:** each new file starts with the same 5-line copyright/SPDX header as `src/game.ts`, plus `// Ported from: src/<file>.c`.
- **State:** no module-level mutable state. All game state lives in `ctx.game` (`src/game/world.ts`), and functions take `ctx: Ctx` (or `g: GameWorld` for pure logic).
- **C integer semantics** are mandatory. Use `src/core/int.ts` (`u8 s8 u16 s16 u32 s32 idiv`) wherever the C narrows, wraps or divides. `JE_byte`=u8, `JE_shortint`=s8, `JE_integer`=s16, `JE_word`=u16, `JE_longint`=s32, `JE_real`=float32, `ulong`=64-bit.
  - Assignments to the scratch globals (`temp`, `temp2`, `temp3`, `tempW`, `b`, `x`, `y`) always wrap to their C type.
- **RNG:**
  - Use `ctx.rng` only, keeping the C call order exactly, including short-circuit evaluation (`a && b > mt_rand()%11` draws only when `a` is true).
  - `mt_rand() % m` with a possibly-negative `m` uses `rngMod` (Task 2).
  - `roundf` uses `roundf32` (Task 2).
- **Unported branches:** branches the demos never take (two-player, galaga, network, record_demo, smoothie filters, absent event types) are not ported. They are marked `// TODO(sp4): <C file:line>`, and if reached they `throw new Error('unported: <C ref>')`. Never silently skip a branch the demos might take. When unsure, port it.
- **Uninitialised or out-of-bounds C reads:** reproduce the neighbouring-memory behaviour where the survey says it matters. Otherwise mirror what real data provably does, and add a comment.
- **Golden tests** skip (`describe.skip`) when oracle files are absent, like the existing `test/golden/*.test.ts`.
- **Commands:** `pnpm test` and `pnpm typecheck` must pass before every commit.
  - **Parallel waves:** other agents may be editing other files in this checkout at the same time. Run your own test files plus `pnpm typecheck`. If an unrelated file from another in-flight task breaks typecheck, note it in your report rather than editing it.
  - **Staging:** only `git add` your own files. Never `git add -A` or `git add .`.
- **Commit messages** end with: `Claude-Session: https://claude.ai/code/session_01JXJ4hjEXrGM5Vja2B6e4Wz`

## Review Focus

1. **Scratch-global clobbering** (survey §5.1). For example, `JE_doSP` overwriting `temp` inside the shot/enemy collision. A port that uses locals here diverges only when an enemy is hit by a damaging shot. Task 6 adds a test pinning it, and Task 14 verifies it through the demo goldens.
2. **The `lives` alias** of front-weapon power (survey §5.2). Events 33 and 45 read it through RNG comparisons. Task 2 adds a test of the accessor.
3. **Negative-modulus RNG** (survey §5.5) at `JE_makeEnemy` start positions. Task 2 tests `rngMod`, and Task 9 uses it.
4. **Map pointer spill** reads (survey §5.3) at the left and right edges and at the wrap. Task 5 tests them.
5. **Demo abort mid-level** with any key, returning to the title, then playing the next demo. Task 15 adds a browser smoke test and a golden scenario that injects a key mid-demo.

**Interfaces:**
- Produces:
  - **Oracle env vars** (spec §3.1): `OT_HASH`, `OT_STATE`, `OT_DEMO`, `OT_RAW_EVERY`, `OT_RAW_FRAMES`.
  - **State record:** 16 × u32 LE, in this order: `frame, mtCalls, curLoc, eventLoc, p0x, p0y, p0shield, p0armor, p0cash, enemyOnScreen, liveEnemies, livePlayerShots, liveEnemyShots, liveExplosions, backPos, mapY`.

    - `readStates(path): StateRecord[] | null`, with `StateRecord` an object with the 16 named fields.
    - `STATE_FIELDS` is the ordered list of the field names.
  - **Scenarios:**
    - `SCENARIOS` gains an optional `demo?: number`, `hash?: boolean` and `state?: boolean`. A `demo` scenario selects Demo from the title menu.
    - Add `'demo-1'` … `'demo-5'`, each with `demo: n`, `hash: true`, `state: true`, and `maxFrames` large enough to reach the title idle after the demo. To measure it, run once with a large max and record the frame index of the first idle-menu frame after the demo.

    - Verify the item index in `src/screens/title.ts` (MENU_ITEM_DEMO) and the menu-nav golden.
- **The C side:**
  - `mtrand.c` gains `unsigned long oracle_mt_calls`, incremented in `mt_rand`.

    - `rngMod(r: number, m: number): number`: C `unsigned long % int`. A negative `m` converts to `2^64 + m`; since `r < 2^32 < 2^64 + m`, the result is `r`. For `m > 0` it is `r % m`, and `m == 0` throws.
